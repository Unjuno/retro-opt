## Solver validation

### Random acyclic stochastic graph

`experiments/solver_random_dag_crosscheck/` で6-state stochastic DAGを200ケース生成し、value iterationと全deterministic stationary policy総当たりを照合した。

- cases: 200
- mismatches: 0
- max absolute error: 0.0 s

### Retry / self-loop SSP

`experiments/solver_retry_crosscheck/` でself-loopを持つretry問題を200ケース生成し、解析解とvalue iterationを照合した。

- cases: 200
- mismatches: 0
- max absolute error: 約 `9.54e-12 s`

これらはsmall-state validationであり、一般の大規模cyclic SSP全体の完全な証明ではない。

### Resource dependency

`experiments/resource_dependency_toy/` で、optional item pickup、gold pickup、item sale、shop purchase、boss retry riskを同一state spaceへ統合した。

局所的にはpickupは時間増だが、resourceの補完関係を利用して複数pickupを取り、装備を保持したまま別資源を購入するpolicyが全体最適になった。

このfixtureはDQ6実測値ではなく、次の性質をsolverが扱えることを確認するためのもの。

- itemを保持するcombat value
- itemを売るeconomic value
- goldによるpurchase feasibility
- 複数resourceの補完関係
- boss failure/retryによるdownstream risk

## Observation constraint

hidden RNGが違っても人間から同じObservationに見えるstate群では同一actionを強制する、小規模用の全policy総当たりreference solverを追加した。

これにより、内部RAM/RNGをmodel解析へ利用しつつ、Competition policyへclairvoyant informationを漏らさない境界を明示できる。

## DQ6 resource model

`games/sfc/dq6/model/state_dimensions.json`、`docs/resource-optimization.md`、`docs/resource-model.md` を用意した。

DQ6全体探索では、少なくとも以下を将来価値を持つstateとして保持する。

- HP / MP / alive / status
- EXP / level / stats / vocation / proficiency
- bag / personal items / equipment
- item orderやslotがcommand timeへ影響する場合の配置
- gold / sellable assets / reachable shops / future purchases
- chest・itemの回収/未回収/消費/売却状態
- story flags / route unlock
- remaining route / encounter opportunities
- human-observable history

「必要itemがないと進めない」「gold不足で買えない」等はreward penaltyではなくaction feasibilityとして表現する。

`src/retro_opt/games/dq6/feasibility.py` では、gold / item / flag / alive memberをaction preconditionとして判定し、purchase / seed use / inventory / equipment等のresource effectをimmutable stateへ適用できるようにした。

## Conservative resource dominance

資源状態が増えるとstate explosionが起きるため、`src/retro_opt/solver/resource_dominance.py` を追加した。

単純な「速い + itemが多い」を支配とはみなさない。inventory layout / equipment / flags等、単調性をまだ証明していない状態は `exact_signature` が一致する場合のみ比較し、gold等の明示的にmonotoneと宣言した軸だけで枝刈りする。

これにより、itemが増えたせいでmenu cursor distanceが変わるようなstateを誤って消すことを避ける。

## DQ6 sensitivity experiments

### `dq6_early_break_even`

追加戦闘1回がEXP閾値を跨ぐことで、後続から何秒削れば期待値上得になるかを計算。

### `dq6_early_policy`

現在EXPによってfight/skip境界が変わることを確認。固定ruleではなくstate-dependent policyになる。

### `dq6_early_horizon`

同じEXPでも、ボスまでに残るencounter opportunity数によってactionが変わり得ることを確認。

### `dq6_metal_kill_sensitivity`

Metal Slimeのappearanceとkill successを分離。アモール北B2の約20%という公開参考値はappearanceであり、EXP獲得確率ではないため、撃破率を別パラメータとして扱う。

初期v0で曖昧だった `metal_probability` 表記は、appearance rateと混同しないよう `metal_reward_probability` に改名した。

### `dq6_410g_shop_feasibility`

アモール北の410G回収と、ホラービースト後に参考chartで購入される720Gの鉄の盾について、売却・操作時間・下流価値を除外した純粋なpurchase feasibilityを計算した。

- 盾1枚: starting gold 310–719G で410G回収が購入可否を変える
- 盾2枚: starting gold 1030–1439G で410G回収が購入可否を変える

これはroute optimalityではなく、「どのgold帯で410Gがshop action setを変えるか」という構造境界である。

## Route objective experiment

`experiments/repeated_attempt_objective/` で、成功run単体の速さと「目標successを1回得るまでの期待壁時計時間」が一致しないことを確認した。

IID attemptの単純モデルでは、success probabilityを `p`、成功時平均を `Ts`、失敗時平均を `Tf` とすると、期待壁時計時間は

```text
Ts + ((1 - p) / p) * Tf
```

となる。将来のChart Atlasでは平均タイム・完走率・target突破率等と並べて保持する。

## 現時点で判明した設計上の要点

1. `EXP >= Xなら狩る`のような単一閾値だけでは不十分。
2. policyはEXPだけでなく、item / equipment / gold / stats / remaining route等のresource stateに依存する。
3. itemにはcombat・消費・route unlock・resale・menu配置という複数の価値があり、早期にgold換算へ圧縮してはいけない。
4. 局所的に遅い複数の寄り道が、資源の補完関係によって全体最適になる場合がある。
5. 「これがないと勝てない/買えない/進めない」はrewardではなくaction feasibilityで扱う。
6. gold pickupの価値は所持金帯によって不連続に変わり、shop action set自体を変える。
7. item数が多いstateを無条件に優越とみなせない。menu layout等の非単調要因を保持する必要がある。
8. Metalのappearance rateとreward probabilityを混同しない。
9. hidden RNGを解析へ使っても、Competition policyではObservation単位でactionを拘束する。
10. 最速成功runと、目標successまでの期待壁時計時間最小routeは一致しない場合がある。
11. small medal等の累積資源は、序盤segment終端では価値が確定せず、交換地点までdownstream valueを伝播させる必要がある。
12. 実測前は最適タイムを主張せず、decision boundaryとmeasurement priorityを出す。
